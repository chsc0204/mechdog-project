# MechDog Project — Dog C (목적지 유도·에스코트) + DB/인프라

> ⚠️ **진행 중인 프로젝트**입니다. 2026 미래내일 일경험 지원사업(ESG지원형) 청년피지컬AI일경험 팀 프로젝트의 일부이며, 최종 발표(5회차)까지 계속 업데이트됩니다.

## 담당 및 역할
- **로봇 파트**: Dog C — 목적지 유도·에스코트 (Hiwonder MechDog, ESP32 기반 사족보행 로봇)
- **겸직 파트**: 팀 전체 DB 설계·통합 (PostgreSQL + MQTT)

---

## 무엇을 만들었나

방문자를 목적지까지 안내하고, 도착 시 인사하며, 터치센서로 다음 안내를 준비하는 **완전 무선 에스코트 로봇 시스템**입니다.

```
목적지 입력 → 웨이포인트 이동 (자동 확장형 장애물 회피 포함)
   → 도착 → 인사 동작
   → 터치센서로 다음 안내 확인 (타임아웃 안전장치 포함)
   → 모든 상태를 MQTT로 실시간 발행 → PostgreSQL 저장
```

## 기술적으로 해결한 문제들

프로젝트 진행 중 마주친 실제 엔지니어링 문제와 해결 과정입니다.

- **공식 API 문서 없이 BLE 통신 프로토콜 역분석**: 제조사 공식 앱의 디컴파일된 코드를 분석해 이동/동작/센서조회 명령 체계(`CMD|N|params|$`)를 알아내고, USB 없이 완전 무선으로 로봇을 제어하는 파이썬 클라이언트를 직접 구현
- **로봇 자체 펌웨어(MicroPython) 확장**: 기존 이동 명령 체계에 없던 기능(제자리 회전, 터치센서 상태 조회, MP3 재생)을 로봇 실행 프로그램에 직접 추가
- **실측 기반 캘리브레이션**: 이론값이 아닌 실제 로봇 속도(초당 이동거리, 회전각도)를 측정해 웨이포인트 정확도 개선 — 이 과정에서 좌/우 방향 코드가 반대로 매핑된 실제 조향 버그를 발견 및 수정
- **하드웨어 제약을 고려한 설계 전환**: 원래 계획이었던 카메라 기반 실시간 추적이 하드웨어 불안정성으로 어려워지자, 웨이포인트+거리센서+터치센서 조합으로 설계를 재구성해 안정적인 대안 아키텍처 확립
- **자동 확장형 장애물 회피 알고리즘**: 정면 거리센서 하나만으로, 좁은 장애물과 넓은 장애물(벽 등)에 모두 대응 가능하도록 재시도할수록 회피 반경이 커지는 로직 설계
- **팀 전체 DB 스키마 통합**: 4개 파트(출입인증/대화/에스코트/보안관제)가 독립적으로 설계한 데이터 요구사항을 하나의 PostgreSQL 스키마로 통합, 공용 세션 원장 테이블 설계 및 이벤트 매칭 키(`msg_id`) 도입
- **블루투스 → WiFi 통신 전환**: 팀 통합 요구에 맞춰 로봇 통신을 WiFi(UDP)로 전환. 이동 루프가 CPU를 독점해 WiFi 수신이 굶는 문제를 발견하고, 루프에 짧은 양보(`sleep(0.01)`)를 넣어 이동 중 정지 명령 신뢰성 확보
- **로봇 자체 안전장치(Tier1) 결함 발견 및 수정**: 근접정지·통신두절 정지가 이동 루프에 의해 즉시 덮어써져 실제로는 작동하지 않던 문제를 코드 분석으로 발견. 이동 상태 변수를 직접 해제하는 방식으로 수정하고, 노트북 측에 keepalive(0.3초 재전송)를 도입해 통신이 끊기면 1초 내 자동정지하도록 설계
- **ESP32-CAM 스트리밍 복구**: 보드 패키지 버전 호환성(2.0.14), PSRAM·파티션 설정, 픽셀 포맷(RGB565) 문제를 하나씩 해결해 폰 핫스팟 환경에서 영상 스트리밍 확인
- **로봇 시점 비전 인식 평가 및 대안 설계**: 출발지 복귀용 표식 인식을 위해 YOLOv8 기본 모델을 로봇 카메라(240×240, 바닥 높이)로 평가 → 낮은 시점·저해상도로 오인식(텀블러→냉장고 등)이 많아 부적합 판단. 구성품 색깔 공 + HSV 색 인식으로 전환하고, 화면 클릭으로 공·벽·바닥의 실제 색 값을 측정해 인식 범위를 설계(벽 타일과 색상 H값으로 분리). 반사광·매트·잡음 오인식을 볼록 껍질, 채움 비율, 크기 범위, 다중 프레임 확인으로 차례로 제거
- **카메라 영상 지연 원인 분석**: 공을 보고도 지나치는 현상을 로그로 추적해 영상이 1초 이상 늦게 도착하는 것을 확인. 수신/처리 스레드를 분리해 항상 최신 프레임만 처리하도록 구조 변경 (가짜 카메라 부하 테스트로 지연 누적이 사라짐을 검증)
- **경로 기록 모드**: 시간 기반 경로를 계산으로 만들면 회전 오차·U턴 반경 문제가 생겨, 키보드로 직접 몰아 가는 길/돌아오는 길을 기록하고 그대로 재생하는 도구로 전환 (팀 목적지 코드 기준 저장 → 이후 B파트 연동 시 그대로 사용)
- **Docker 기반 인프라 구축**: PostgreSQL + MQTT 브로커 + MQTT→DB 브릿지를 Docker Compose로 통합 관리, 컨테이너 간 네트워킹 이슈(localhost vs 서비스명) 해결

## 실행 방법

**1. 인프라 실행**
```
docker compose up -d
```

**2. WiFi 설정**
`wifi_config.example.py`를 복사해 `wifi_config.py`로 이름을 바꾸고 WiFi 이름/비밀번호 입력
(카메라 아두이노 코드의 ssid/password도 같은 값으로 설정)

**3. 로봇에 펌웨어 업로드**
Hiwonder Python Editor로 `main_wifi.py`(+ `wifi_config.py`)를 로봇에 업로드 후 `main.py`로 저장, 재부팅

**4. 이동 테스트** (로봇 IP는 `wifi_move_test.py` 상단에서 수정)
```
python wifi_move_test.py
```

**5. 경로 기록** (시연 공간에서 목적지마다 1회)
```
python record_route.py
```
목적지 선택 → 가는 길 몰기 → Enter → 돌아오는 길 몰기 → Enter → 저장

**6. 에스코트 실행**
```
python escort_wifi.py
```
목적지 코드 입력 (예: `meeting_room_1`). 진단 명령: `touch`(터치센서), `bow`(인사동작), `home`(카메라 복귀), `spin`(제자리 회전)

**7. DB 확인**
```
python check_recent_events.py
```

## 알려진 이슈
- MP3 스피커 모듈: 파일명 규칙·통신·포트는 전부 정상 확인됐으나 실제 음향 출력이 안 되는 상태 (하드웨어 교체 필요 추정)
- 정면 거리센서 1개만 사용 중이라, 낮거나 얇은 장애물(예: 책상다리) 감지에 한계 있음
- 카메라 센서 설정상 RGB565로 스트리밍 중 (ESP32에서 소프트웨어 JPEG 변환 → 고해상도에서 FPS 저하). JPEG 모드 재시도 예정
- 카메라 센서가 자동 노출·화이트밸런스 설정을 거부(HTTP 500) → 노트북에서 밝기 보정. 설정 화면의 "OV2640" 표기와 달리 다른 센서일 가능성
- 카메라 영상 지연 1초 이상 → 수신/처리 분리로 개선, 실기 재검증 필요
- 제자리 회전(CMD|9)은 회전량이 시간에 비례하지 않음 (정밀 각도 제어 불가, 탐색 용도로만 사용)
- 아이폰 핫스팟 사용 시 "호환성 최대화"를 켜야 ESP32(2.4GHz 전용)가 접속 가능
